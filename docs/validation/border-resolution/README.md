# 共有セル罫線の解決と検証

入力基準: `origin/main` `2996f6c`。計画書の調査コミット `9dd0eb8` より新しい main を取得し、既存変更のない状態から `fix/shared-cell-border-resolution` で実装した。Microsoft Excel とユーザーの実帳票はこの環境にない。以下の優先順位はExcel仕様の実測結果ではない。

## 実装と暫定優先順位

Core `BorderConflictResolver` が通常辺と結合外周断片を同じ候補へ変換する。同一直線・同じclipの候補をソートし、端点イベントと優先順位付き集合で重なった区間だけの勝者を選ぶ。候補Eに対してソート・走査を行い、セル全対比較や空セル全域展開は行わない。ページはページ単位、連続出力は辺だけを保持して解決済み命令を逐次返す。メモリはO(E)であり、定メモリではない。

| 比較順 | 採用する罫線 |
| --- | --- |
| 指定あり／なし | 指定あり。nullは対向辺を消さない |
| Double／非Double | Double。各ストロークの幅とは別に比較 |
| 同じDouble区分 | 幅が大きい側 |
| 同幅・非Double | Solid > DashDotDot > DashDot > SlantDashDot > Dashed > Dotted > Hair |
| 同順位の隣接辺・異色 | 上側セルの下辺、左側セルの右辺 |
| 同じ側の重複断片 | 開始・終了座標、元アドレス、RGBAの順で決定的に比較 |

白は通常の色として比較し、黒を優先する例外は設けない。styleId・borderId・XML順序・列挙順は優先順位に使わない。完全に同一の候補を集合内で識別するIDは見た目の選択には使わない。

二重線は既存 `GetStrokes` の方向指定なしの対称配置を利用する。保存形式のDouble幅0.75ptは維持し、境界の±0.75ptに2本を置く。公開の単独 `DrawBorderCommand` の内側配置は変更しない。図形輪郭や独立した `DrawLineCommand` はセル罫線の候補に含めない。

破線・点線・斜め一点鎖線は元のパスを勝者区間でclipするため、分割時に元のダッシュ位相を失わない。同じ元候補が続く区間を連結する。Solid/Double/Hairは書式・配置・clipが等しい隣接区間も連結し、異なる候補の破線は単純に連結しない。Core PDFもこのclipを適用する。本体は既存viewportアダプター経由でPDF/PNG/SVG/PSへ渡す。

外側の所有辺は `BorderNeighborIndex` が論理的な行・列境界で検索する。選択されたセル・印刷矩形の外周に接する辺だけを投影し、所有者の文字や背景は出力しない。非表示セルの辺はここで復活させない。通常ページと繰り返し見出しの配置ごとに取得し、ページ間の解決状態は共有しない。配置座標の丸め誤差のみ8倍の機械精度で吸収し、0.0000001pt幅の列を区別する。

結合セルの読み取り規則は変更していない。元セル外周の明示断片を保持し、リーダーだけの辺を結合矩形全体へ補完しない。右下セルの右・下辺や明示的な空白を維持する。条件付き書式は本体で確定したスタイルを使い、Coreに評価機能は追加しない。

保存済みの通常セルが選択セルに隣接する場合は、罫線を変更・消去する条件付き書式も本体で評価する。範囲・ページ選択によって未評価の元罫線を復活させない。既存の候補予算に数え、外側のfont/fillには適用せず、保存されていない外側セルを新たに展開しない。

範囲指定のない連続キャンバスは線の実幅を含めて確保し、外周のDoubleを切らない。明示範囲・用紙端のclipは拡張せず、他ページの内容は含めない。改ページでセルを途中切断しても新しい辺は作らない。

## 再現入力と検証方法

`create-fixture.py` はZIP内のXMLを直接生成する。保存ライブラリの隣接辺自動補完を介さず、異なるborderId、同じ見た目の異なるstyleId、上下・左右Double、白黒、結合部分辺、行列既定書式、条件付き書式の明示消去を5シートに収録した。

入力: `tests/ExcelRenderer.Tests/SampleInputs/BorderResolution/border-conflicts.xlsx`。SHA256は `artifact-hashes.json` を参照。単体画像は144/288DPI・倍率1/0.5で断面を計測する。

修正前に追加した10件のテストはすべて失敗した。両側Doubleは論理4ストロークであり、今回の144DPI断面では中央2本が接するため3本のインク帯として観測された。保存画像・失敗TRXを `before/`, `before.log`, `before.trx` に保持する。修正後は一つの共有線命令から2ストローク・2本の帯になる。

`BorderResolutionTests` は8線種×8線種×縦横の128組、幅優先、clip分離、座標誤差、交差、保存xlsxのCore経路を検証する。本体テストは画像断面、片側None、異色、部分結合、狭い列、破線位相、CF消去、選択外所有辺、非表示列、印刷範囲、途中改ページ、反復見出し、複数印刷範囲、連続出力を検証する。

既存Readerモデルの基準ファイルは変更しない。罫線命令変更に伴うPNG/SVGの期待値は別の `ReaderGolden/border-artifacts.json` に隔離する。Markdown期待値と歴史的 `artifacts.json` は保持する。`BorderGolden.cs` で同じ既存入力の修正前後を出力し、差分を記録する。

既存15ブックの修正前出力は歴史的期待値と全件一致した。修正後の32成果物に差分があり、うち16件はPNGである。`compare-golden.py` で96DPIの全変更画素を検査し、罫線周辺マスク外の変更は0画素だった。マスクは変換と同じ明示フォントで列幅を読み、最終命令の周囲に旧Doubleの内側配置とAAを含む余裕を取っている。これは文字や塗りつぶしの広範囲変更がない検査であり、Excelの正解画像との比較ではない。差分画素数と入力・成果物の対応を `golden-differences.json`、差分PNGを `golden-pixel-diffs/` に保持する。

代表共有DoubleをPNG・保存SVGの再ラスタライズ・PDF・PSへ出力した。PDFはPoppler、PSはGhostscriptで288DPIに変換し、交点から離れた断面にいずれも2本の帯を確認した。PDFとPNG/PSではAAによる1画素の差があり、画像の完全一致は要求していない。数値は `raster-sections.json`、出力は `after/shared-double.*` を参照。

## 性能測定

`BorderBenchmark.cs` と `benchmark-input.json` を使い、変更前後のReleaseランタイムで同じモデル仕様からSVGを生成した。通常表は200×20、結合表は200行×20列を2行ずつ結合、連続表は2000×20。通常表は実線、残りはDouble。ページ表はレイアウトと描画を含め、連続表は実際の遅延命令経路を使う。

計測時はビルド・テスト・他の描画を止めた。各ケースで診断1回、診断なしウォームアップ2回、計測5回を実施した。診断カウンターのオーバーヘッドは時間・割当量の中央値に含めない。入力仕様とDLLのSHA256、環境、各回の値を `benchmark-before.jsonl` / `benchmark-after.jsonl` に保持する。割当量は `GC.GetTotalAllocatedBytes`、ピークは同一プロセスの累積 `PeakWorkingSet64` であり、ケース単独のピークではない。

| ケース | 時間中央値 前→後(ms) | 割当量 前→後(MiB) | プロセスピーク 前→後(MiB) | SVG合計bytes 前→後 | 候補→確定区間 |
| --- | --- | --- | --- | --- | --- |
| 通常表 | 177.59 → 44.79 | 29.79 → 47.76 | 82.55 → 73.80 | 1,554,280 → 28,727 | 16,240 → 288 |
| 結合表 | 119.19 → 58.01 | 47.05 → 42.67 | 86.39 → 74.54 | 2,546,680 → 39,832 | 12,240 → 188 |
| 連続表 | 1575.56 → 181.13 | 293.82 → 88.99 | 192.39 → 107.27 | 35,043,433 → 470,313 | 160,000 → 2,022 |

通常表の割当量は増えており、全ケースでメモリや速度が改善したという主張はしない。初回の実装では通常表の時間も約31%増加していたため、完全一致・非重複区間の高速経路と位相のない辺の連結を追加した。初回の生データも `*-initial.*` に保持している。初回と最終回の変更前中央値にも差があるため、この単一環境の測定から5%等の厳密な性能目標達成は判定しない。通常表の割当増加は今後の最適化余地として残す。

最終コードは `dotnet build ExcelRenderer.slnx -c Release -t:Rebuild --no-restore --verbosity:minimal -m:1` で警告0・エラー0を確認した。ツールのバージョンと基準コミットは `environment.json`、実行した検証の集計は `verification.json` を参照。

再測定時は `run-probe.py benchmark --source-root <変更前または後のルート> --output <保存先> --build-only` で両ランタイムを先に構築する。`source scripts/test-fonts.sh` の後、保存先の `runtime/BorderProbe.dll` に同じ `benchmark-input.json` を渡して順番に実行する。`run-probe.py golden` は同じ要領で既存入力の画像とハッシュを取得する。プローブ用csprojは一時領域へ作成し、製品の依存関係・配布内容は変更しない。

## 未検証の範囲

Excel画面・Excel印刷/PDFとの比較、リーダーだけの指定を結合外周全体へ補うべきかの判断、ユーザー帳票に固有の通常線欠落原因は未検証。二重線の角・T字・十字はストローク数と端点を検証しており、Excelと同じ接合形状を保証するものではない。独立した異なるclipの配置は統合しない。

範囲外の未保存空セルへ条件付き書式だけで辺を生成するケースと、範囲外の大きな結合セルのリーダーから離れた外周に条件付き書式が適用されるケースは、今回の外側CF評価追加の対象外。範囲外の行列既定スタイルだけが所有する未実体化の辺も追加検証が必要。既存の保存セル・結合外周断片を使う経路は維持している。

この修正は共有辺の二重描画と描画順依存を解消するもので、通常罫線の欠けをすべて修正した、Excel完全互換になったという主張はしない。
